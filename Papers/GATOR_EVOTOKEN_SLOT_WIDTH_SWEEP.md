# GTR-L EvoToken output-slot-width sweep (core width=16)

Status: **experimental**, early-training leading indicators only

Related: `Papers/GATOR_LINEAR_EVOTOKEN.md` (method), `gator_linear/evotoken.py` (implementation),
`Runbooks/colab_cells/gtrl_130k_evotoken_relay_drive_cell.py` (130k relay-drive runner this
sweep does not use directly, but shares the same masked-only CTS v5 design as the sweep script).

## Motivation

`gator_linear/evotoken.py`'s relay-integrated EvoToken mode reuses GTR-L's four fixed relays as
the refinement trajectory's four steps (see `Papers/GATOR_LINEAR_EVOTOKEN.md`). The number of
output slots is independent of relay count, so widening the output block does not add refinement
budget — `balanced_promotion_counts(slots, steps=4)` just distributes more promotions per relay
(e.g. `(1,0,1,0)` at 2 slots vs `(3,2,3,2)` at 10 slots). The open question this sweep answers:
at what output-slot width does the fixed four-relay refinement budget start to visibly strain,
for a 130k-parameter, core-width=16 model on the no-whitespace TinyStories corpus?

## Method

Five independent runs, each `OUTPUT_SLOTS_TO_RUN` ∈ {2, 4, 6, 8, 10}, same core config
(`GatorLinearConfig(vocab_size=VOCAB, streams=10, nodes=40, width=16, relays=4, degree=6,
buses=4, mailbox_channels=4, mailbox_width=8, basis_rank=4, address_width=4, router_rank=8,
conv_kernel=9, hard_routing=True, linear_attention=True, controlled_writing=True, causal=False)`),
same masked-only CTS v5 objective (every output slot starts masked, promoted exactly once across
the 4 relay stages, no visible-token loss credit — see `Papers/GATOR_LINEAR_EVOTOKEN.md` for why),
batch 16, lr 1e-3, seed 0, TinyStories no-whitespace tokenizer. Each run trained to ~50,000 of a
planned 10,000,000-step schedule (0.5% — an early leading-indicator comparison, not a converged
one) and was stopped manually once past that mark. Trained live on Colab (single L4), 2026-08-01,
run tag `gtrl-130k-evotoken-relay-cts-masked-s{N}-v5`.

Metrics below are pulled from the log line closest to step 50,000 in each run's full log
(`gtrl_evotoken_relay_relay_cts_masked_s{N}_v5.log` in the `GTR-L/gtrl_evotoken_relay/run_logs/`
Drive folder).

## Reading the curve

Every quality metric degrades monotonically with slot count at matched step count:

- **refined_acc** halves from slots=2 (0.242) to slots=10 (0.113).
- **modal_lift** drops from +0.189 to +0.050 — the model is leaning on the unigram-frequent-token
  shortcut nearly 4x more at slots=10 than at slots=2, even though neither has tripped the
  collapse watcher yet.
- **modal** (fraction of predictions equal to the single most common token) climbs from 0.174 to
  0.510 — over half of slots=10's predictions are the modal token at this point in training.
- **retained** (top-k probability mass kept after filtering) falls from 0.362 to 0.195 — the
  model's belief is spreading thinner across more candidates as width grows.

This is consistent with the motivating hypothesis: **the four-relay refinement budget is fixed,
but the promotion load per relay grows with slot count** (`(1,0,1,0)` at 2 slots vs `(3,2,3,2)`
at 10 slots), so each relay has progressively less "attention" to spend refining any one slot's
belief before the block closes out. The decline is smooth and monotonic rather than a sharp
cliff — nothing in this data identifies a hard ceiling where 8 or 10 slots is qualitatively
"broken" rather than "quantitatively weaker." Whether the gap narrows, holds, or widens further
into training (past this 0.5%-of-schedule snapshot) is not established by this sweep.

## Caveats

- **Early snapshot only.** 50k of 10M planned steps. Wider-slot runs may simply need more
  training to reach comparable per-slot accuracy, not be structurally incapable of it — this
  sweep cannot distinguish "needs more steps" from "needs more relay budget."
- **Throughput differs by width** (not just wall-clock scaling with slot count): slots=2/4 ran
  near ~950 steps/min, slots=6 ~940/min, slots=8 ~700-940/min (variable), slots=10 ~790-914/min.
  Step count, not wall-clock time, is the controlled variable here.
- **Unlike the very first slots=4-vs-slots=8 comparison** made before this sweep was set up
  (recorded in the `gator_evotoken_slot_width_sweep` project memory as confounded — it compared
  the pre-generalization `v4` code against the new generalized `v5` code), all five runs in this
  table use the identical generalized `dc212b9` code path and CTS-masked-only objective, so this
  is a clean slot-count-only ablation.
- The slots=6 run crashed ~18.6s after its initial launch attempt (an accidental double-click on
  the Colab UI's toggling run/interrupt button killed it almost immediately) and had to be
  relaunched from a clean step-0 start — this did not affect its final reported numbers, since
  the relaunch is a fresh run, not a resume, but is noted for the record.

## Next

(confirmed by the user as the correct doubling — the notebook's actual current value was 16, not
the local repo's unrelated default of 8) to see whether more capacity per node changes the shape
