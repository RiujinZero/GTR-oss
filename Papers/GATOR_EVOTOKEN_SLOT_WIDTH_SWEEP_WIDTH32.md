# GTR-L EvoToken output-slot-width sweep (core width=32)

Status: **experimental**, early-training leading indicators only

Related: `Papers/GATOR_LINEAR_EVOTOKEN.md` (method), `gator_linear/evotoken.py` (implementation),
`Papers/GATOR_EVOTOKEN_SLOT_WIDTH_SWEEP.md` (the matched width=16 sweep this report extends).

## Motivation

The width=16 sweep found that quality degrades monotonically as output-slot count grows, consistent
with the fixed four-relay refinement budget getting spread thinner across more slots. This sweep
repeats the same five-point slot sweep with core `width` doubled from 16 to 32, to test whether more
per-node capacity offsets that strain, and whether the effect is uniform across slot counts or
concentrated where the promotion schedule is least even.

## Method

Same as the width=16 sweep (`GatorLinearConfig(vocab_size=VOCAB, streams=10, nodes=40, relays=4,
degree=6, buses=4, mailbox_channels=4, mailbox_width=8, basis_rank=4, address_width=4, router_rank=8,
conv_kernel=9, hard_routing=True, linear_attention=True, controlled_writing=True, causal=False)`),
with `width=32` (doubled from 16), same masked-only CTS v5 objective, batch 16, lr 1e-3, seed 0,
TinyStories no-whitespace tokenizer. `OUTPUT_SLOTS_TO_RUN` ∈ {2, 4, 6, 8, 10}, each trained to ~50,000
of the planned 10,000,000-step schedule and stopped manually once past that mark. Trained live on
Colab (single L4), 2026-08-01, run tag `gtrl-130k-evotoken-relay-cts-masked-s{N}-v5`. Total model
parameters: 232,205 at width=32 vs 129,197 at width=16 (both core configs shared across all slot
counts — slot count changes only the output block and promotion schedule, not core width).

Metrics below are pulled from the log line closest to step 50,000 in each run's full log
(`gtrl_evotoken_relay_relay_cts_masked_s{N}_v5.log` in the `GTR-L/gtrl_evotoken_relay/run_logs/`
Drive folder).

## Width=16 vs width=32, matched slot count

| slots | refined_acc (w16→w32) | Δ relative | modal_lift (w16→w32) | Δ relative |
|---:|---|---:|---|---:|
| 2  | 0.2422 → 0.2559 | +5.7%  | +0.189 → +0.203 | +7.4%  |
| 4  | 0.1846 → 0.1914 | +3.7%  | +0.123 → +0.130 | +5.7%  |
| 6  | 0.1283 → 0.1491 | **+16.2%** | +0.077 → +0.098 | **+27.3%** |
| 8  | 0.1211 → 0.1279 | +5.6%  | +0.064 → +0.071 | +10.9% |
| 10 | 0.1133 → 0.1207 | +6.5%  | +0.050 → +0.058 | +16.0% |

Every slot count improves under width=32, but the gain is not uniform. Slots=2 and 4 — the two
configs with the most "regular" promotion schedules relative to their slot count (`(1,0,1,0)` and
`(1,1,1,1)`, each relay handling at most 1 promotion) — see modest single-digit-percent gains.
Slots=6, 8, and 10 all have uneven promotion schedules (some relays handle 2-3 promotions, others
half that), and see larger gains, led by slots=6's `(2,1,2,1)` schedule at +16.2%/+27.3%. Slots=8's
schedule, `(2,2,2,2)`, is technically even in count-per-relay but at double the per-relay load of
slots=4 — it shows a smaller gain than slots=6 or 10, suggesting evenness of load *and* absolute
promotion count both matter, not just unevenness alone. This is consistent with (but does not by
itself prove) the hypothesis that extra core width relieves relay-level capacity strain most where
the promotion schedule concentrates load unevenly or heavily on individual relays — see
`Papers/GATOR_EVOTOKEN_SLOT_WIDTH_SWEEP_WIDTH64.md` (pending) for whether this pattern holds, grows,
or reverses at width=64, which is the cleanest way to separate "more width helps uneven schedules
more" from "more total parameters helps more when the model is already more capacity-starved" (the
same total-parameter-count question applies at every width, since wider slot counts have lower
`params_per_slot` at fixed core width).

## Caveats

- **Early snapshot only**, same as the width=16 sweep — 50k of 10M planned steps, single seed, no
  repeated trials. The width=16-vs-32 gaps above could narrow, hold, or widen with more training.
- **Not a controlled parameter-count ablation.** Width=32 has ~1.8x the total parameters of width=16
  (232,205 vs 129,197). This sweep cannot distinguish "width specifically helps" from "more total
  parameters helps, and width happens to be how we added them" — that requires comparing against a
  differently-shaped config with a matched parameter count, which hasn't been run.
- **Throughput** was not separately logged for this sweep in a form worth reporting; wall-clock time
  to reach ~50k steps ranged roughly 57-60 minutes across runs, similar to the width=16 sweep.
- Slots=2's run continued well past 50k (to ~step 149k) before being stopped, due to an unrelated
  Colab frontend reconnect issue that delayed the stop action — this did not affect the reported
  datapoint, which is still the log line closest to step 50,000, not the final step reached.

## Next

Width=64 sweep (slots 2, 4, 6, 8, 10) is planned to test whether the width=16→32 pattern above
continues, flattens, or reverses, and to bring in each run's total parameter count as an explicit
